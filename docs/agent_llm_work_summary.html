AID-FIT Agent 구현 흐름 정리

이 문서는 AID-FIT 추천 시스템을 Agent 관점에서 설명합니다. Agent는 화면이나 검색 엔진 자체가 아니라, 사용자 입력, 이미지 분석, 옷장 컨텍스트, RAG 검색 결과, LLM 응답 생성을 하나의 추천 의사결정 흐름으로 묶는 조율자입니다.

문서 위치: docs/agent_llm_work_summary.html 구현 기준: 현재 Backend 코드 최신화: 2026-08-23 핵심 관점: LangGraph Agent, 계약, 상태, 라우팅
Full-stack

입구와 출구

사용자 요청을 받고, 이미지 URL과 옷장 아이템을 정규화한 뒤 Agent 응답을 화면에 표시할 수 있는 형태로 받습니다.

VLM

이미지 해석

패션 서비스 요청에 이미지가 있으면 색상, 소재, 핏, 패턴, 무드, 계절감 같은 패션 속성을 추출합니다.

RAG

후보 검색

Agent가 만든 검색 요청에 따라 사용자 옷장, 무신사 상품, 또는 둘을 합친 후보 리스트를 반환합니다.

Agent

흐름 제어

LLM의 구조화 판단을 검증해 일반 대화와 패션 서비스를 나누고, 기존 검색 결과 재사용 또는 새 검색 경로를 선택합니다.

Agent가 하는 일

현재 구현의 중심은 AidFitAgentPipeline입니다. 이 파이프라인은 LangGraph 상태 머신으로 구성되어 있으며, 각 노드는 전체 데이터를 직접 새로 만들기보다 필요한 상태만 읽고 다음 단계에 필요한 상태를 채웁니다.

입력 검증 LLM 의도 분류 이미지 존재 여부 판단 VLM 호출 여부 결정 LLM 질의 정제 LLM 검색 계획 이전 RAG 재사용 RAG 요청 조립 fallback 검색 제어 스타일 랭킹 LLM 최종 응답 검증

중요한 점은 Frontend가 closet, musinsa, hybrid를 직접 고르는 구조가 아니라는 것입니다. 운영 모드에서는 LLM이 사용자 문장, 대화 내역, 이미지 분석 결과, 옷장 아이템, use_closet_style, 사용자 프로필을 보고 검색 대상과 이전 결과 재사용 여부를 구조화된 JSON으로 결정합니다.

전체 처리 흐름

요청은 FastAPI 서비스 계층을 지나 Agent로 들어갑니다. LLM이 먼저 일반 대화와 패션 서비스 요청을 분류합니다. 일반 대화는 검색 없이 답변하고, 패션 서비스 요청만 이미지 분석·질의 정제·검색 계획·RAG 단계로 넘어갑니다.

1. 입력query, image_urls, closet_items, user_profile을 받습니다.
2. 검증입력과 대화 내역을 검증하고 이미지·옷장 존재 여부를 계산합니다.
3. 의도 분류LLM이 general_chat 또는 fashion_service를 반환합니다.
4. 일반/VLM일반 대화는 바로 답변합니다. 패션 요청에 이미지가 있으면 VLM을 실행합니다.
5. 질의 정제LLM이 현재 질문, 최근 대화, VLM 결과를 독립적인 검색 문장으로 합칩니다.
6. 검색 계획LLM이 이전 RAG 재사용 또는 closet/musinsa/hybrid 새 검색을 결정합니다.
7. 응답LLM이 후보 상품 안에서만 추천 문장과 스타일 가이드를 생성하고, Agent 계약으로 검증합니다.
input_validation -> context_check -> intent_classifier ├─ general_chat -> general_chat_response -> END └─ fashion_service -> image 있음? vlm -> fashion_item_check : VLM 생략 -> query_refiner -> retrieval_planner ├─ reuse -> reuse_rag_results -> style_ranker └─ retrieve -> build_rag_request -> closet_rag | musinsa_rag | hybrid_rag -> rag_result_check -> fallback_search(최대 1회) -> final_response -> END

연속 대화와 API 진입점

LangGraph 한 번의 실행은 요청 단위이므로, 이전 대화를 자동으로 이어 주는 책임은 채팅 API와 DB 계층에 있습니다. 같은 Agent를 사용하더라도 호출하는 API에 따라 대화 내역을 자동으로 복원하는지가 달라집니다.

일회성 추천

POST /api/v1/recommendations

현재 요청만 처리합니다. 공개 요청에 conversation_id가 없고 DB에서 이전 메시지를 자동 조회하지 않으므로, 다음 요청의 “그중”, “아까 추천한 것” 같은 표현은 자동으로 연결되지 않습니다.

연속 채팅

POST /api/v1/chats/{conversation_id}/messages

같은 conversation_id의 최근 메시지와 직전 RAG 컨텍스트를 DB에서 불러와 Agent에 전달합니다. 질문과 답변도 다시 저장하므로 다음 요청과 서버 재시작 이후에도 대화 흐름을 이어갈 수 있습니다.

1) POST /api/v1/chats -> conversation_id = "chat-123" 2) POST /api/v1/chats/chat-123/messages { "query": "검은 재킷에 어울리는 바지 추천해줘", "image_urls": [] } 3) POST /api/v1/chats/chat-123/messages { "query": "그중 더 저렴한 걸로 골라줘", "image_urls": [] } 서버가 chat-123의 이전 메시지와 RAG 후보를 복원하므로 두 번째 질문의 "그중"을 직전 추천 후보로 해석합니다.
채팅 API가 자동으로 하는 일처리 내용
최근 대화 복원같은 대화의 최근 메시지를 최대 20개까지 시간순으로 불러와 LLM 입력에 전달합니다.
직전 검색 컨텍스트 복원assistant 메시지에 내부 저장된 RAG 후보, 검색 질의, 검색 대상을 가져옵니다.
후속 질문 판단LLM이 기존 후보로 충분하면 관련 항목만 골라 재사용하고, 새 주제나 부족한 후보이면 RAG를 다시 수행합니다.
대화 저장현재 사용자 질문과 Agent 답변을 각각 메시지로 저장해 다음 턴에서 다시 사용합니다.
내부 데이터 비공개_agent_context는 DB에만 보관하고 채팅 조회 API의 공개 payload에서는 제거합니다.

따라서 ChatGPT처럼 이어지는 화면은 반드시 /chats/{conversation_id}/messages를 사용해야 합니다. 이는 LangGraph 기능의 차이가 아니라, 어떤 API 진입점이 대화 상태를 DB에서 복원해 주는지의 차이입니다.

입력 계약

Full-stack이 Agent에 넘기는 기본 계약은 AgentRequest입니다. 이미지는 파일 본문이 아니라 URL 배열로 전달하고, 이번 추천에서 기준이 되는 옷장 아이템은 closet_items로 전달합니다.

{ "user_id": "user_001", "query": "화이트 니트랑 어울리는 바지 추천해줘", "image_urls": [], "closet_items": [ { "closet_item_id": "closet_001", "category": "bag", "color": "black", "material": "pvc", "fit": "none", "pattern": "graphic", "mood": "street", "sense_of_season": "summer" } ], "use_closet_style": true, "user_profile": { "age_group": "20s", "preferred_styles": ["minimal", "casual"] } }
필드Agent 관점의 의미
query사용자의 자연어 의도입니다. 비어 있으면 외부 AI를 호출하지 않고 INVALID_INPUT으로 종료합니다.
image_urls패션 서비스 요청으로 분류되고 이미지가 있을 때 VLM 경로로 들어갑니다. 없으면 빈 배열입니다.
closet_items이번 요청에서 참고할 보유 아이템입니다. retrieval planner LLM이 closet 또는 hybrid 판단에 활용합니다.
use_closet_style기존 옷장 스타일과 취향을 랭킹에 반영할지 결정합니다. false이면 query 관련성 보너스를 더 중시합니다.
user_profile검색 계획, RAG 필터, 랭킹 보너스에 사용하는 사용자 취향 정보입니다.
chat_historyPipeline 내부 입력입니다. 채팅 API가 최근 user/assistant 메시지를 시간순으로 만들어 자동 전달합니다.
previous_rag_*Pipeline 내부 입력입니다. 직전 후보·질의·검색 대상을 채팅 DB에서 복원해 후속 질문 재사용 판단에 전달합니다.

공개 AgentRequest는 일회성 추천 계약입니다. chat_history와 previous_rag_results는 ChatService가 내부적으로 AidFitAgentPipeline.run()에 전달하는 연속 대화용 상태입니다.

State 구조

Agent는 한 번의 추천 요청을 AgentState에 담아 노드 사이를 이동시킵니다. State는 입력값, 중간 판단, 외부 모듈 결과, 최종 응답을 분리해서 들고 있기 때문에 디버깅과 모듈 교체가 쉬워집니다.

상태 그룹주요 키설명
Full-stack 입력user_id, query, image_urls, closet_items, use_closet_style, user_profile요청에서 직접 들어온 값입니다. Agent 판단의 출발점입니다.
대화 컨텍스트chat_history, previous_rag_results, previous_rag_query, previous_retrieval_target후속 질문의 지시어를 해석하고 이전 검색 결과 재사용 여부를 판단하는 입력입니다.
컨텍스트 판단has_image, has_closet_items, is_fashion_itemVLM 호출 여부와 비의류 이미지 차단에 사용합니다.
LLM 추론intent, intent_reason, resolved_query, retrieval_action, retrieval_target, retrieval_reason, selected_rag_item_refs일반/패션 분류, 독립 질의, 재사용/재검색, 검색 대상과 선택 후보를 보관합니다.
VLM/RAG 결과vlm_items, rag_query, rag_request, rag_results, has_rag_result, rag_reused이미지 분석 결과와 검색 요청/응답, 이전 후보 재사용 성공 여부를 보관합니다.
후처리ranked_items, final_response, error정렬된 후보와 최종 응답입니다. 내부 에러는 public 응답 계약으로 변환됩니다.
호환 필드image_url, closet_item_id, recommendation_target, rag_items기존 단일 이미지/기존 코드 경로와의 호환을 위해 유지합니다.

LLM 기반 의도·검색 계획

운영 모드(USE_MOCK_AI=false)에서는 Agent 노드에 키워드 목록을 두고 경로를 고르지 않습니다. LlmService가 Gemini의 구조화 출력을 받고, Agent가 Pydantic 계약으로 검증한 값만 LangGraph 분기에 사용합니다.

LLM 단계입력구조화 출력과 분기
classify_intent()현재 query, 최근 대화, 이미지 첨부 여부general_chat이면 일반 답변 노드로 종료하고, fashion_service이면 VLM/검색 흐름으로 진행합니다.
refine_query()현재 query, 최근 대화, VLM 의류 속성QueryRefinement.query에 지시어와 이미지 정보를 반영한 독립적인 resolved_query를 반환합니다.
plan_retrieval()원문/정제 query, 이전 RAG 후보, 옷장·프로필·VLM 컨텍스트RetrievalPlan으로 reuse|retrieve, closet|musinsa|hybrid, 선택 후보 ref를 반환합니다.
compose_general_chat()일반 질문과 최근 대화RAG 없이 자연어 답변을 생성하고 공개 AgentResponse 형태로 감쌉니다.

USE_MOCK_AI=true일 때만 외부 모델 없이 테스트할 수 있도록 결정론적 mock 판단을 사용합니다. 실제 서비스 라우팅은 USE_MOCK_AI=false와 GEMINI_API_KEY 설정을 전제로 합니다.

VLM과 RAG 계약

Agent → VLM

이미지 분석 요청

VLMRequest는 image_urls만 전달합니다. 사용자 query는 VLM에 넘기지 않고, VLM은 이미지에서 보이는 패션 속성만 분석합니다.

{ "image_urls": [ "https://cdn.aidfit.com/images/item_001.jpg" ] }
VLM → Agent

패션 메타데이터 반환

반환값은 VLMResponse입니다. is_fashion_item=false이면 Agent는 RAG를 호출하지 않고 에러 응답을 만듭니다.

{ "items": [ { "category": "top", "color": "white", "material": "knit", "fit": "oversized", "mood": "minimal", "sense_of_season": "spring", "is_fashion_item": true } ], "is_fashion_item": true }
Agent → RAG

검색 요청 조립

새 검색이 필요할 때 Agent는 LLM이 만든 resolved_query, VLM 결과, 옷장 아이템, 프로필, 검색 대상, 필터를 하나의 RAGRequest로 묶습니다.

{ "user_id": "user_001", "query": "화이트 니트랑 어울리는 바지 추천", "retrieval_target": "hybrid", "vlm_items": [], "closet_items": [], "use_closet_style": true, "filters": { "preferred_styles": ["minimal", "casual"] }, "top_k": 30 }
RAG → Agent

후보 리스트 반환

RAG는 상품 후보와 점수를 반환합니다. 무신사 상품은 클라이언트에서 바로 열 수 있도록 product_url이 필수입니다.

{ "items": [ { "source": "musinsa", "name": "세미 와이드 데님 팬츠", "image_url": "https://image.msscdn.net/example.jpg", "product_url": "https://www.musinsa.com/products/10001", "final_score": 0.91 } ], "message": "success" }

retrieval planner가 action=reuse를 반환하면 새 RAGRequest를 만들지 않습니다. selected_item_refs가 실제 직전 후보에 존재하는지 검증한 뒤 해당 후보만 사용합니다. 존재하지 않는 ref, 빈 선택, 손상된 이전 후보는 새 RAG 경로로 자동 전환됩니다.

랭킹과 fallback

RAG 결과가 있으면 style_ranker_node가 다시 정렬합니다. 기본 점수는 final_score, metadata_score, similarity_score 순서로 사용하고, 인증 사용자의 저장된 좋아요와 후보 상품의 콘텐츠 유사도를 공통 보너스로 더합니다. 옷장·프로필 보너스는 use_closet_style 값에 따라 달라집니다.

상황랭킹 방식
좋아요 유사도좋아요의 상품 ID·상품 URL·이미지 URL로 product_vectors 또는 사용자 소유 closet_items를 일괄 조회합니다. 색상·소재·핏·패턴·무드·계절만으로 스타일 전용 문장을 만들고 Gemini의 SEMANTIC_SIMILARITY 임베딩 70%와 명시적 속성 일치 30%를 결합합니다. 조회되지 않은 상품은 저장된 상품명을 폴백으로 사용하며, 브랜드·카테고리·가격은 임베딩과 점수 모두에서 제외합니다. 가장 가까운 좋아요와 상위 3개 스타일 패턴을 합산해 최대 0.20을 더하고, 임베딩 장애 시에는 속성 비교만으로 계속 추천합니다.
use_closet_style=true옷장을 사용자 취향으로 보고 후보별 상위 3개 스타일 유사도를 계산합니다. 옷장 취향 55%와 상의–바지·아우터–상의처럼 조합 가능한 카테고리의 코디 호환성 45%를 결합해 최대 0.20을 더합니다. 코디 요청에서는 25%/75%로 호환성을 더 중시합니다. 스타일 의미 임베딩과 색상·계절·소재·무드 조화 규칙을 함께 사용하고, 별도의 동일·유사 상품 제거 또는 감점은 적용하지 않습니다.
use_closet_style=false기존 옷장 취향보다 현재 query와 후보 상품 메타데이터의 직접 관련성을 더 봅니다.
이전 RAG 결과 재사용“더 저렴한 것” 같은 현재 후속 지시가 장기 취향보다 우선하도록 retrieval planner가 선택·정렬한 순서를 유지합니다.
RAG 결과가 없음style, season 필터를 제거하고 top_k를 최소 20으로 넓혀 1회 재검색합니다.
fallback 후에도 결과 없음empty 응답을 반환합니다.

LLM의 역할

현재 LlmService는 최종 추천 문장만 만드는 것이 아니라 Agent의 의미 기반 판단 단계 전체를 담당합니다. 모든 판단 호출은 Gemini structured output을 사용하고, 반환값은 전용 Pydantic 모델로 다시 검증합니다.

메서드역할검증 계약
classify_intent()일반 채팅과 AID-FIT 패션 서비스 요청을 분리합니다.IntentClassification
compose_general_chat()일반 대화 요청에 RAG 없이 답변합니다.GeneralChatAnswer → AgentResponse
refine_query()대화 문맥과 VLM 속성을 합쳐 독립적인 검색 query를 만듭니다.QueryRefinement
plan_retrieval()이전 후보 재사용/새 검색과 검색 대상을 결정합니다.RetrievalPlan + 실제 candidate ref 검증
compose_recommendation()서버가 순서를 확정한 상품에 추천 이유와 스타일 가이드를 생성합니다.AgentResponse + 서버 순서 재조립
  • 모든 Gemini 판단 호출은 responseMimeType: application/json과 단계별 responseSchema를 사용합니다.
  • 이전 RAG 후보는 planner 입력에 최대 20개를 전달합니다. 최종 생성에는 코드 랭커가 확정한 상품만 전달합니다(채팅 기본 5개, 홈 8개).
  • Gemini가 상품을 누락하거나 재배치해도 서버가 원래 랭킹 순서로 복원하며, 후보에 없는 상품명·가격·URL은 응답에 들어가지 않습니다.
  • 일반 채팅 응답도 기존 공개 계약을 유지하기 위해 빈 추천 배열을 가진 AgentResponse로 반환합니다.
LLM intent JSON -> IntentClassification -> LangGraph 분기 VLM + history + query -> QueryRefinement -> resolved_query previous RAG + context -> RetrievalPlan -> reuse 또는 retrieve ranked_items 상위 N개 확정 -> Gemini 추천 이유 JSON -> candidate item_id/image_url로 이유만 재매칭 -> 서버 랭킹 순서로 재조립 -> AgentResponse 검증 -> Frontend 응답

에러 응답

내부 노드는 AgentError 형태로 에러를 만들지만, 외부 응답은 기존 AgentResponse 계약에 맞춰 status=error, 빈 추천 리스트, style_guide=null 형태로 반환합니다.

코드발생 위치의미

현재 구현 기준 주의사항

문서의 흐름은 실제 Agent 코드 기준입니다. 다만 외부 AI/RAG 시스템은 아직 adapter 경계만 열려 있고, 기본 실행은 mock 구현을 사용합니다. 팀 연동 시에는 아래 지점을 먼저 확인하면 됩니다.

영역현재 상태연동 시 확인할 점
VlmService USE_MOCK_AI=true 기본값에서는 URL 기반 mock 분석을 반환합니다. _external_analyze_many()를 실제 vision API 호출로 교체하고 VLMResponse 계약을 지켜야 합니다.
RagService RAGRequest는 closet, musinsa, hybrid를 받지만 mock 검색은 임시 무신사형 카탈로그를 순환 반환합니다. _external_search_request()에서 retrieval target, filters, top_k를 실제 검색 조건으로 반영해야 합니다.
LlmService USE_MOCK_AI=false이면 의도 분류부터 최종 답변까지 Gemini structured output을 사용합니다. 모든 decision schema를 유지하고, 최종 상품은 후보의 item_id 또는 image_url로 재매칭해야 합니다.
연속 대화 ChatService가 최근 메시지와 내부 RAG 컨텍스트를 DB에서 복원합니다. 프론트 채팅 화면은 /chats/{conversation_id}/messages를 사용해야 하며, 운영 DB에는 채팅 테이블 migration이 필요합니다.
디버깅 AidFitAgentPipeline.run(..., return_trace=True)로 응답, VLM/RAG 결과, intent, resolved_query, retrieval_action, 판단 이유를 볼 수 있습니다. Frontend/API 응답은 기본적으로 final_response만 받으므로 trace는 내부 확인용으로 사용합니다.

실행과 검증

기본값은 외부 호출 없이 동작하는 mock AI입니다. 실제 LLM 기반 의도 분류·질의 정제·검색 계획·일반 채팅·최종 추천을 확인하려면 .env에서 아래 값을 설정합니다.

USE_MOCK_AI=false GEMINI_API_KEY=your_key_here GEMINI_MODEL=gemini-3-flash-preview GEMINI_BASE_URL=https://generativelanguage.googleapis.com/v1beta GEMINI_TIMEOUT_SECONDS=30

주요 검증 명령은 다음과 같습니다.

python -m pytest -q python -m compileall -q app tests

현재 구현 검증 결과는 전체 58개 테스트 통과입니다. 일반 채팅의 VLM/RAG 생략, LLM 정제 query 사용, 검색 대상 제어, 이전 RAG 선별 재사용, 새 질문 재검색, 잘못된 후보 ref의 안전한 재검색 전환을 포함합니다.
