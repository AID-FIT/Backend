# 검색 계층 트러블슈팅 — 저장소를 갈아끼울 때 사라진 것들

ChromaDB에서 pgvector로 옮기며 **저장소 코드가 아니라 그 위에 얹혀 있던 보정 계층**이
따라오지 않았다. 검색은 성공하고 결과도 나오기 때문에 오랫동안 드러나지 않았다.

**핵심 한 줄** — 저장소를 바꾸면 사라지는 것은 쿼리가 아니라 **쿼리 위에 얹은 판단**이다.
별칭 확장, 메타데이터 가중치, 중복 제거, 인덱스 탐색 폭. 전부 새 구현에 없었다.

[08 §7](./08-recommendation-quality.md)에서 `refresh_seed`가 같은 식으로 사라진 적이 있다.
그때 "목록을 만들어 두지 않아 또 놓쳤다"고 적었는데, 실제로 더 있었다.

---

## 1. 구현이 둘이고, 임베딩 모델까지 다르다

### 두 파일은 대체 관계다

| | `rag_service_final.py` | `app/services/pgvector_rag_service.py` |
| --- | --- | --- |
| 저장소 | ChromaDB (로컬 파일) | Supabase pgvector |
| 임베딩 | `jhgan/ko-sroberta-multitask` | `gemini-embedding-001` |
| 차원 | 768 | **1536** |
| 실행 | 로컬 SentenceTransformer | HTTP API |
| 성격 | 한국어 특화 SBERT | 다국어 범용 |

`settings.rag_vector_backend`로 갈린다.

```python
if settings.rag_vector_backend == "pgvector":
    return await self._search_pgvector(request)

# 정적 카탈로그 경로는 chromadb를 끌고 온다.
from rag_service_final import search as vector_search
```

다시 쓴 이유는 성능이 아니다. `rag_service_final`이 `chromadb`와
`SentenceTransformerEmbeddingFunction`을 import하는데, 그게 PyTorch를 끌고 와
서버리스 함수 크기 한도를 넘겼다. 임베딩을 HTTP로 바꾸고 검색을 SQL로 옮겼다.

### "같은 벡터DB니까 괜찮다"가 성립하지 않는다

ANN 검색 자체는 서로 대체 가능하다. 그런데 **임베딩 모델이 함께 바뀌었다.**
768차원 한국어 특화 모델과 1536차원 다국어 범용 모델은 **비교 자체가 불가능한 다른 의미 공간**이다.
카탈로그 문서가 전부 한국어인데 한국어 특화에서 범용으로 옮겼다.

> 저장소를 바꾸는 작업에 임베딩 모델 교체가 끼어 있으면 그건 두 개의 변경이다.
> 검색 품질이 달라져도 어느 쪽 탓인지 가릴 수 없다.

그리고 ChromaDB는 **검색 엔진 + 메타데이터 필터 + 임베딩 함수를 한 덩어리로** 제공한다.
pgvector는 `<=>` 연산자만 준다. 나머지는 직접 짜야 하고, 그게 §2다.

## 2. 따라오지 않은 계층

### 증상

검색은 성공한다. 결과도 나온다. 그런데 "검정"을 요청해도 흰 옷이 위에 오고,
같은 상품이 피드에 두 번 뜬다.

### 원인 — 네 가지가 통째로 비어 있었다

| 팀원 구현에 있던 것 | pgvector 구현 | 결과 |
| --- | --- | --- |
| `expand_query` — 한↔영 별칭 200여 개 | 없음 | 질의를 원문 그대로 임베딩 |
| `build_search_text` — 질의 + VLM + 옷장 + 선호 스타일 합성 | 없음 (`query`만) | 옷장·취향이 검색에 반영 안 됨 |
| `calculate_metadata_score` — 카테고리 .20 / 종류 .20 / 계절 .15 / 색 .15 / 핏·무드 .10 | 없음 | 메타데이터가 순위에 관여 못 함 |
| `deduplicate_musinsa` — `product_url` 기준 | 없음 | 같은 상품이 두 번 뜬다 |

**가장 조용했던 것**은 메타데이터 점수다. `nodes.py`의 랭커는 이미 그 값을 읽고 있었다.

```python
def _base_ranking_score(self, item):
    for key in ("final_score", "metadata_score", "similarity_score"):
        value = item.get(key)
```

그런데 pgvector의 `_to_item`이 이렇게 내보내고 있었다.

```python
"similarity_score": round(similarity, 4),
"metadata_score": None,
"final_score": round(similarity, 4),   # 유사도 그대로
```

`final_score`가 유사도와 같으니 랭커는 **가중치 계층이 있는 줄 알고 유사도만 다시 정렬**했다.
계약은 맞는데 내용이 빈 형태라 어디서도 에러가 나지 않았다.

중복 제거도 실측으로 확인된다. 카탈로그 12,794행에 고유 `product_url`은 **10,500개** —
2,294개 상품이 두 번씩 들어 있고, 그대로 피드에 두 번 오를 수 있었다.

### 해결

순수 로직을 `app/services/catalog_matching.py`로 뺐다. chromadb도 DB 세션도 들어오지 않는다.
**저장소를 또 갈아끼워도 이 계층은 따라와야 하기 때문이다.**

`expand_query`는 옮기면서 한 군데 고쳤다. 원본은 리스트 원소 단위로 중복을 걸러서
질의 문장 안에 이미 있는 낱말이 별칭으로 또 붙었다. 낱말 단위로 거른다 —
같은 낱말이 여러 번 실리면 임베딩에서 그 축만 부풀어 오른다.

> `rag_service_final.py`에도 같은 표가 남아 있다. 그 파일은 chromadb를 import해
> 이 환경에서 테스트가 스킵되므로 손대지 않았다. static 경로를 걷어낼 때
> 그쪽이 공용 모듈을 import하도록 바꾼다.

## 3. `hnsw.ef_search = 40` — 액세서리가 사라진 진짜 원인 ⭐

### 증상

홈 피드에 **신발·가방·모자가 하나도 없다.** 상의·바지·아우터만 나온다.

### 배제한 것들

먼저 데이터와 모델을 의심했는데 전부 정상이었다.

| 확인 | 결과 |
| --- | --- |
| 프로덕션 카탈로그 | 12,794건이 7종에 고르게, `category` NULL 0건 |
| Gemini 임베딩 | 질의·문서 모두 1536차원 정상 |
| 임베딩의 카테고리 편향 | **없음.** 가방 +0.6445, 모자 +0.6408로 오히려 1·2위 |
| LLM 질의 정제 | 3회 모두 카테고리를 넣지 않음 |

### 원인 — 인덱스가 40건에서 멈춘다

pgvector의 `hnsw.ef_search`는 HNSW가 그래프에서 훑는 폭이고 **기본값이 40**이다.
그보다 큰 `LIMIT`을 걸어도 인덱스는 40건 언저리만 돌려준다.

운영 DB에 직접 붙어 홈 질의를 그대로 실행한 결과다.

| | 결과 |
| --- | ---: |
| `LIMIT 400` 질의가 반환한 건수 | **40건** |
| 그중 고유 `product_url` | 39개 |

그 40건의 분포가 문제다.

```
아우터 21 · 바지 14 · 모자 3 · 신발 1 · 상의 1 · 가방 0 · 원피스/스커트 0
```

`ef_search`를 400으로 넓히면 같은 질의가 400건을 돌려주고 7종이 모두 담긴다.

| 설정 | 반환 건수 | 카테고리 |
| --- | ---: | --- |
| `ef_search=40` (기본) | 40 | 5종, 가방·원피스 0건 |
| `ef_search=400` | 400 | **7종 전부** |

실제 코드 경로(`RagService._search_pgvector`)로 돌린 최종 결과:

```
100건 / 아우터 35 · 바지 29 · 가방 16 · 모자 7 · 신발 6 · 상의 3 · 원피스 4 · 중복 0
```

### 왜 라운드로빈으로 못 고치나

[08 §3](./08-recommendation-quality.md)의 `_spread_by_category`도,
[09 §2](./09-home-filtering.md)의 `_fill_home_feed`도 **이미 검색된 것을 나눠 담을 뿐**이다.
상위 후보에 모자가 없으면 아무리 섞어도 모자는 생기지 않는다.
**균형은 보장된 적이 없었고 기대되고 있었을 뿐이다.**

### 해결

질의마다 `SET LOCAL`로 후보 수 이상 넓힌다.

```python
ef_search = max(candidate_limit, MIN_EF_SEARCH)
await db.execute(text(f"SET LOCAL hnsw.ef_search = {int(ef_search)}"))
```

`SET LOCAL`인 이유는 pgbouncer다. 세션 단위로 걸면 커넥션을 돌려쓸 때 다른 요청까지 따라 바뀐다.

**후보 상한도 함께 올려야 한다.** `candidate_limit`은
`min(max(limit * CANDIDATE_MULTIPLIER, limit), MAX_CANDIDATES)`인데, 상한이 뽑는 수의
배수에 못 미치면 새로고침 회전([08 §7](./08-recommendation-quality.md))이 겹친다.
`limit=100`일 때 `MAX_CANDIDATES=200`이면 창이 두 개뿐이라 짝수 번째 새로고침이
처음 본 화면을 그대로 돌려준다. 400으로 올려 네 창이 나오게 했다.

공식은 `candidate_limit_for()` 함수로 꺼냈다. 인라인 수식으로 두면
다음에 풀 크기를 바꿀 때 또 조용히 깨진다.

## 4. 여기서 한 번 크게 틀렸다

`ef_search`를 넣고 배포했더니 **홈 추천이 통째로 실패했다.** 원인을 이렇게 판단했다.

> pgvector는 `hnsw` 접두사를 예약하므로(`MarkGUCPrefixReserved`), 확장 라이브러리가
> 아직 로드되지 않은 새 커넥션에서 `SET LOCAL hnsw.ef_search`를 첫 문장으로 보내면
> Postgres가 에러를 낸다. 트랜잭션 안에서 에러가 나면 뒤따르는 SELECT까지 함께 죽는다.

그럴듯했고, 증상과도 맞았다. 되돌렸다.

**실측으로 반증됐다.** 새 커넥션에서 `SET LOCAL hnsw.ef_search = 400`은 정상 통과한다.
Postgres가 점 있는 이름을 placeholder로 받아 두기 때문이다.
같은 시점에 `SHOW hnsw.ef_search`는 `UndefinedObjectError`를 내지만 `SET`은 다르다.

진짜 원인은 전혀 다른 곳이었다 — [12 §1](./12-works-locally-fails-deployed.md)의 애노테이션 문제다.

> **확인할 수 없는 가정으로 프로덕션을 건드렸다.** DB에 붙어 한 줄 실행하면 5분에
> 끝날 검증을, 그럴듯한 추론으로 대신했다. 그 결과 원인이 아닌 것을 되돌리고
> 진짜 원인은 그대로 둔 채 한 번 더 배포했다.
>
> 테스트로 검증할 수 없는 변경(DB에 보내는 문장, 외부 API 계약)은 **따로 떼어 올리고
> 실제 환경에서 확인한다.** 같은 커밋에 섞으면 무엇이 원인인지 가릴 수 없다.

## 5. 목업이 검색을 가리고 있었다

### 증상

`GET /products`가 항상 같은 상품 12건을 돌려준다.

### 원인

`RagService.search`가 `_mock_catalog()`를 돌고 있었다. 목업 분기가 아니라
**메서드 본문이 통째로 목업**이었고, `/products`가 그걸 쓰고 있었다.

더 넓은 문제는 배포 코드에 `USE_MOCK_AI` 분기가 서비스 세 곳에 박혀 있었다는 것이다.
목업 경로는 응답을 검증하고 다듬는 뒷부분까지 우회한다.
**실제 경로와 목업 경로가 서로 다르게 굳어, 목업에서만 통과하는 버그가 생긴다.**

### 해결 — 지우되 옮긴다

프로덕션에서 527줄을 걷어냈다.

| 파일 | 이전 | 이후 |
| --- | ---: | ---: |
| `llm_service.py` | 877줄 | **575줄** |
| `rag_service.py` | 412줄 | **222줄** |
| `vlm_service.py` | 368줄 | **333줄** |

결정적 동작은 지우지 않고 `tests/fake_ai.py`로 옮겼다. 파이프라인 테스트 39개가
`LlmService(use_mock_ai=True)`를 더블로 쓰고 있어 그냥 지우면 테스트가 무너진다.

**옮기면서 구조를 바꿨다.** 더블은 모델을 부르는 지점 하나만 가로챈다
(`_generate_structured`, `_external_*`). 응답을 검증하고 다듬는 뒷부분은 프로덕션 코드가
그대로 돈다 — 그래야 테스트가 실제로 도는 코드를 확인한다.

`/products`는 지우지 않고 실제 pgvector 검색으로 바꿨다. 처음으로 실제 상품을 반환한다.

## 6. 틀렸던 또 하나의 가설

"임베딩이 액세서리를 밀어낸다"고 추정했다. 홈 질의가 의류 문장이고 문서에
`카테고리: 모자` 같은 줄이 있으니 상위가 옷으로 쏠릴 것이라는 논리였다.

카테고리별로 60건씩 표본을 뽑아 실제 코사인 유사도를 재봤다.

```
가방 +0.6445 · 모자 +0.6408 · 바지 +0.6389 · 아우터 +0.6352
원피스/스커트 +0.6253 · 상의 +0.6243 · 신발 +0.6199
```

**정반대였다.** 가방과 모자가 1·2위다. 상위 25%에서도 가방 23건·모자 21건으로 가장 많고
상의 8건·신발 5건이 가장 적다. 임베딩은 액세서리를 밀어내지 않는다.

그럴듯한 서사는 측정을 대신하지 못한다.

## 체크리스트

저장소나 검색 엔진을 바꿀 때 확인한다.

- [ ] 저장소 코드 말고 **그 위에 얹은 보정 로직** 목록을 먼저 적었는가
- [ ] 임베딩 모델이 함께 바뀌지 않는가 — 바뀐다면 그건 두 개의 변경이다
- [ ] 새 구현이 기존 계약(`final_score` 같은 키)을 **값까지** 채우는가, 껍데기만 맞추는가
- [ ] ANN 인덱스의 탐색 폭(`hnsw.ef_search`, `ivfflat.probes`)이 `LIMIT` 이상인가
- [ ] 후보 상한이 뽑는 개수의 배수인가 (새로고침 회전이 겹치지 않으려면)
- [ ] 중복 제거가 새 구현에도 있는가
- [ ] 라운드로빈·분산 로직이 **검색 결과에 없는 것을 만들어 낼 수 없다**는 것을 아는가
- [ ] 테스트로 검증할 수 없는 변경(DB 문장, 외부 API)을 다른 변경과 섞어 올리지 않았는가
- [ ] 배포 코드에 테스트용 분기가 남아 있지 않은가
